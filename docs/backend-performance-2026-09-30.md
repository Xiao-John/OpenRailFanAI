# Main 后端性能报告 · 2026-09-30

## 1. 结论与云端接入状态

**当前工作区已经接入 SiliconFlow，而且本次真实调用成功。** 现有配置使用
`https://api.siliconflow.cn/v1`，模型和结构化决策模型均为
`deepseek-ai/DeepSeek-V4-Flash`，内部供应商 ID 为 `default`，来自已有 `LLM_*` 配置；
`LLM_MOCK=false`，API 方言自动选择后实际走 `chat_completions`。
本次沿用已有密钥，没有写入或替换用户本轮提供的密钥，也没有在报告中记录密钥。

独立短连接请求成功，耗时约 **3.78 秒**，返回用量为输入 28、输出 2、合计 30 tokens。
随后 20 次真实端到端流式请求均取得 HTTP 200 和 `done`，无错误、降级或截断标志；
请求用量和模型调用记录均非零。因此接入状态已经通过实际请求验证。

主要性能问题是**云端生成等待和部分外部铁路数据查询较慢**。五个主要场景中位耗时
为 12.9～21.4 秒；全部 20 个样本的累计耗时中，生成约占 72%，检索约占 21%，决策约占 7%。
本地规则识别、站名查找和健康接口本身较快。

这份结论适用于当前桌面工作区 Main 后端配置。Android 设备上的独立设置、实际使用的密钥、
网络链路及界面显示耗时没有实测；不能把工作区连接成功扩大为手机端验证通过。

## 4. 首次可见内容与结构化等待

`stage` 进度事件、上游模型首段文字和用户最终可见结果是不同的时间点。
例如交路第一次约 52 毫秒就收到进度，但卡片直到约 12.91 秒的 `done` 才到达。

| 普通流式场景 | 首个 `answer` 事件距请求开始，中位数 | 范围 |
| --- | ---: | ---: |
| 余票 | 9.41 秒 | 9.40～10.00 秒 |
| 大屏 | 4.15 秒 | 1.70～5.14 秒 |
| 知识问答 | 7.07 秒 | 6.21～16.02 秒 |
| 票价 / 里程（各一次） | 3.73 / 1.98 秒 | 单样本 |

交路、经停、批量和包含交路结果的拍车查询沿用现有结构化缓冲机制：
抑制思考增量，模型正文先收集并经过事实冲突、重复保护，卡片随 `done` 交付。
九次含卡片样本中八次完全没有 `answer` 增量；另一次交路只有结束前一条正文。
这符合当前交付路径，不能把没有正文增量误判为请求失败，也不能把上游模型开始输出误报为卡片已经显示。

临时遥测测得，生成开始后约 1.7～7.0 秒出现首段上游文字（不同样本有思考/正文差别），
但仍可能继续等待完整生成。该计时是 SDK 映射后的语义内容，不是网络首字节或设备渲染时间。
单纯改善模型首段速度未必等比例改善结构化卡片等待。

## 5. 数据查询、缓存与本地资源

现有工具指标中所有 45 次计数均为 `ok`，没有工具失败。`ok` 表示工具正常返回，
不代表查到了票、不代表有当日交路，也不构成独立事实准确性审计。
临时包装还观察到预取/参数提前返回，故入口调用数量与正式工具指标数量不是同一口径。

| 工具 | 指标调用数 | 中位耗时 | 观察 |
| --- | ---: | ---: | --- |
| `ticket.query` | 3 | 7.36 秒 | 三次仍为 6.52～7.84 秒，热重复请求没有降到毫秒级 |
| `train.schedule` | 7 | 5.12 秒 | 3.53～6.20 秒，是时刻/交路组合的主要检索等待 |
| `emu.routing` | 8 | 1.42 秒 | 按正式指标统计，非包括提前返回的所有入口调用 |
| `station.screen` | 3 | 11.6 毫秒 | 首次 2.345 秒，后两次 8.4、11.6 毫秒，缓存收益明显 |
| `web.search` | 6 | 0.887 秒 | 本轮范围 0.325～1.260 秒 |
| `ticket.price` | 1 | 1.972 秒 | 单样本 |
| `rail.mileage` | 1 | 29.7 毫秒 | 单样本，本地查询 |
| `station.lookup` | 10 | 2.3 毫秒 | 本地站名查询较快 |

大屏整段检索第一次为 2.35 秒，热请求为 10.4、15.0 毫秒；但端到端分别仍需 9.78、
23.53 秒。缓存解决了检索成本，生成依然主导总时间。源码中的大屏 TTL 为 **600 秒**，
应将结果理解为缓存快照，不能把低延迟宣传为秒级实时数据。

当前 `_rt12306` 还具备原始余票行 300 秒、列车标识/经停/车组详情 3600 秒等进程内缓存。
不能由“存在缓存代码”推断余票主路径所有请求都会命中；本次主路径实测仍慢。
缓存满容量时存在整体清空，尚未看到跨请求的 in-flight 合并；并发突发下的缓存击穿未测试。

采样期间持续探测本次服务 `/health`：**635/635 成功**，中位 4.623 毫秒，
nearest-rank p95 5.556 毫秒，最大 10.432 毫秒。
后端进程 RSS 采样由约 **98.6 MiB** 增至峰值 **150.0 MiB**。
缓存和依赖懒加载会影响这段增长；五分钟测量不能证明存在或不存在内存泄漏。
该 RSS 不含基准客户端、系统、Android 进程。`ps` CPU 采样不足以归因单阶段 CPU 消耗。

单聊天请求进行时服务仍能响应轻量健康检查，未观察到长时间事件循环停顿。
这是每约 0.5 秒采样的结论；微小阻塞可能漏采，也未施加多个聊天请求同时运行的压力。
不据此给出 QPS、最大用户数或横向扩容收益。

## 6. 云端用量与调用结构

20 次端到端请求产生 **25 次高层模型调用**：20 次生成，另 5 次用于知识问答、批量和多轮决策。
确定性快路径承担了 15/20 次决策。没有观察到应用兼容阶梯额外调用。
当前 SDK 默认最多重试 2 次，但本次高层包装和指标无法直接数出 SDK 内部 HTTP 重试，
不能由上述 25 次断言网络传输恰好只有 25 次。

| 用量（不含此前短连接测试） | Tokens |
| --- | ---: |
| 输入 | 55,955 |
| 输出（包含供应商计入的思考等） | 9,096 |
| 合计 | **65,051** |
| 每次端到端请求平均 | 3,253 |

输入占约 86%。相同主要场景的生成提示为 3,232～6,586 字符，当前仍使用完整生成提示，
事实条目数量不限。重复采样没有启用整轮答案缓存，所以每次仍会产生生成用量。
25 次模型指标的 token 总和与 20 次 `done.usage` 总和完全一致。
供应商余额、账单、缓存计费分类和实时单价没有查询，因此不虚报人民币成本。

但它们确实使套件提前中断，后续断言未被验证；不能把这些套件计为通过。
本次未执行完整 `run_all.sh`，未修改测试或生产代码来取得绿色结果。

另有两处测试入口缺口：`test_metrics.py` 没有 `__main__`，现有脚本逐文件执行时
不会调用其中的测试函数；`test_structured_sse_visibility.py` 尚未列入 `run_all.sh`。
本次前者已显式执行函数，后者已单独执行，不受这两处遗漏影响。

现有 `/api/metrics` 已实现，但应按以下口径解释：

- 单进程、近 512 次样本的延迟窗口；次数与 tokens 是进程启动以来累计，不是同一个窗口。
- `completed` 统计流程结束，生成降级/失败或者工具失败也可能进入这一计数，不能直接用它当业务成功率。
- 流式 LLM 的 `finally` 会记录调用，包括取消路径；现有模型失败率并未完整区分失败、取消和正常结束。
- 当前 p95 算法取 `floor((n-1)*0.95)` 索引，3 次时取第二大值；本次脚本用 nearest-rank。
  小样本的两种数值可能差很多，报告不混用。
- 缺少首次内容、卡片交付、缓存命中/未命中、预取使用率和 SDK 重试次数。
  本次临时遥测补足一部分时间点，但不替代正式长期监控。

## 8. 后端优化优先级与边界

以下为基于实测的建议，尚未实施；预计收益需要后续对照测量，不能预先承诺秒数。

| 优先级 | 工作 | 依据与验证要求 |
| --- | --- | --- |
| P0 | 修复回归替身签名和 Main/LM 目录断言；补齐测试入口 | 先恢复可信验证，保持 Main/LM 业务边界；不扩大到客户端修改 |
| P0 | 统一业务成功、工具失败、模型失败、降级、取消的内部指标口径 | 当前 completed/failed 不足以评估真实可靠性；不变更既有 SSE 字段含义 |
| P1 | 减少结构化路径生成负担，评估已有精简提示及有效输出预算 | 本轮生成占约 72%；保持卡片投影、缓冲和重复事实保护，不能重新流出冲突铁路事实 |
| P1 | 跟踪时刻/余票的实际网络子请求与缓存未命中原因 | 时刻约 5.1 秒、余票约 7.4 秒；区分初始化、抓取、回退，验证按日期/车次复用 |
| P1 | 按完整配置隔离复用 LLM HTTP 连接并明确关闭生命周期 | 当前每次构建 AsyncOpenAI，缺乏显式共享池；已有上游流关闭应继续保持，不能串用用户密钥 |
| P2 | 改善云端决策路径及真正重叠的预取 | 当前先 await planner.decide 再 start prefetch，无法隐藏决策等待；日期和参数必须匹配，未用请求要取消 |
| P2 | 跨请求工具查询合并与有界缓存淘汰 | 保持日期、动作和配置隔离；取消一个等待者不能误取消其他用户共享查询 |
| P2 | 将抓取守卫同步 DNS 移出事件循环，保留原有安全校验 | `_http.assert_public_url` 同步 getaddrinfo；本轮未观察明显停顿，但潜在慢 DNS 应专项验证 |

暂不推进 Python→Kotlin 整体迁移，不改 Android、WebUI、展示协议、默认连接、LM 配置、
版本、签名或验收规则。优化可以先在内部生成预算、工具调度、连接复用和指标上进行。

仍需单独安排：多用户并发压测、长期缓存/内存测试、真实故障与取消测试、Android 实机端到端计时、
结果准确性与实时性审计。批量部分失败、定向重试和块式动作行为也没有被本轮性能采样验证。

2026-09-25 的[历史云端基线](cloud-api-baseline-2026-09-25.md)主要场景中位耗时曾为
6.91、10.68、16.41、16.26、9.85 秒。本轮部分场景更慢，但日期、上游波动、缓存状态、
生成输出长度和当前源码均未受控，不能据此归因某次修改导致性能退化。
