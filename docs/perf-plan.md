## 一、实测诊断：瓶颈不在"预筛选的工具调用"

对 3 类典型问句逐阶段计时（`/tmp/latency_probe.py`），冷/热各跑一遍：

| 问句 | 轮次 | 总耗时 | 意图 | 抽取 | **检索** | 生成（首字） |
|---|---|---|---|---|---|---|
| G1今天由哪组担当 | 第 1 次（冷） | 35.4s | 9.3s | 10.7s | **1.0s** | 14.5s（1.1s） |
| G1今天由哪组担当 | 第 2 次（热） | 11.9s | 4.6s | 2.4s | **2.1s** | 2.9s（1.0s） |
| G1经停哪些站 | 第 1 次（冷） | 9.4s | 1.5s | 1.5s | **2.0s** | 4.5s（0.9s） |
| G1经停哪些站 | 第 2 次（热） | 8.8s | 1.4s | 2.4s | **0.5s** | 4.4s（1.2s） |
| 北京南站下午有哪些高铁 | 第 1 次（冷） | 52.4s | 1.2s | 22.8s | **0.01s** | 28.4s（1.3s） |
| 北京南站下午有哪些高铁 | 第 2 次（热） | 15.9s | 8.6s | 3.0s | **0.02s** | 4.4s（0.6s） |

**结论 1：检索（工具调用）只占 0.02–2.1s**，因为它已经并发执行 + 有缓存。
用户感受到的"7–8 秒预筛选"，实际是**意图 + 抽取这两次 LLM 往返**（实测 3.8–11.6s）。

**结论 2：冷启动才出现 35s/52s** —— 来自外部工具首次取数（rail_line 首次 19s、
车站大屏 0.5–2s）与 provider 抖动叠加。缓存预热即可消灭这一档。

**结论 3：provider 抖动极大**：同一个 prompt、同一个模型、temperature=0，
意图分类实测 1.2s → 9.3s（同一进程内相邻两次）。

**结论 4：首字很快（0.6–1.3s）**，用户"看不到东西"的时间几乎全部花在**生成之前的等待**。

**结论 5：结构化调用在"白想"** —— 抽取一次的 reasoning tokens 实测 243（在最小 prompt 下
仍占 40/54）。关掉思考后：**抽取 3.3s → 1.1s（中位，3 次）**。小模型更快：
`Qwen3-30B-A3B-Instruct-2507` 1.09s、`Qwen2.5-7B-Instruct` **0.44s**（同一 schema 任务）。

**结论 6：确定性解析已能覆盖大部分问句** —— 用 `docs/ragval/testset.txt` 50 条真实
车迷问法实测：**68% 可由正则给出意图线索或槽位，56% 能直接定意图**（剩下的多是
知识型/站名类，那些本来也不需要检索工具）。

## 二、方案（按 ROI 排序，均为可独立交付的小步）

### P0-1 确定性快路径：意图 + 槽位不再各打一次 LLM ★效果最好

- **做什么**：新增 `pipeline/fastpath.py`，用已有解析器（`od.parse_od`、`dates.normalize_date`、
  `rt.extract_train_code`/`is_train_code`、站点索引、`_wants_stops`/`_screen_direction` 等）
  直接产出 `intent + slots`；**只在"所有信号一致"时才走快路径**，否则回落现有 LLM 两连问。
- **配套**：`PipelineResult`/`done` 事件增加 `planner: "deterministic" | "llm"`，
  便于统计快路径误判率（可回滚的开关 `FASTPATH_ENABLED`）。
- **预期**：覆盖 56–68% 问句，预筛选 **3.8–11.6s → <0.3s**；总耗时 8.8–15.9s → **3–4.5s**。
- **风险**：正则误判（本项目有前科：D09 把"明天下午"当站名）。缓解：只在高置信模式命中时启用；
  demo 测试集回归；保留 `planner` 标记以便定位。

### P0-2 合并意图 + 抽取为一次调用（快路径未命中时）

- **做什么**：`fastpath` 判不出时，一次结构化调用同时产出 intent + question_type + slots
  （一个 schema），并**关闭思考**、精简指令文案（把长说明压到必要项）。
- **预期**：2 次往返 → 1 次；实测抽取 3.3s → 1.1s，整体预筛选 **-2 至 -4s**。
- **风险**：单次输出变长、schema 冲突时更难定位；用现有 `test_pipeline`/`test_routing` 钉住。

### P0-3 投机预取：检索与分类并行

- **做什么**：正则命中车次/站名/OD 时，**立即**并行发起最可能的 1–2 个工具
  （如 `emu.routing` + `train.schedule`），与（可能存在的）LLM 分类重叠；
  分类结论不同则丢弃预取结果（成本 = 一次廉价 HTTP）。
- **预期**：把检索的 0.5–2.1s 完全藏进分类耗时里，**-0.5 至 -2s**。
- **风险**：多打一次外部接口（对 12306 限流敏感）→ 只在正则高置信时预取，且复用现有缓存。

### P1-1 生成侧：先结论、控长度

- **做什么**：生成 prompt 增加"**第一句给结论**；实时型问句正文 ≤200 字（需要细节再展开）"，
  并给 `stream_completion` 显式 `max_tokens` 上限。
- **预期**：生成 2.9–4.4s → ~2s（实测答 237–774 字，长答 14–28s 的尾部由长度决定）。
- **风险**：信息量下降 → 用 R1 测试集复核关键判定点仍在。

### P1-2 感知延迟：让用户立刻看到东西

- **做什么**：检索完成即推一条**事实摘要**事件（不经 LLM），前端在"检索完成"时先渲染
  "已查到：G1 今日担当 CR400BFA-5159 / 经停 7 站…"，随后再流式补答案；
  stage 事件附毫秒数（已有字段，前端未展示）。
- **预期**：首屏可见时间从 8–15s → **1.5–2.5s**；总时长不变但体感完全不同。
- **风险**：摘要措辞需与最终答案口径一致，避免"先说要发车、答案却说已发车"。

### P2 缓存与预热（治冷启动）

| 项 | 现状 | 动作 |
|---|---|---|
| 答案级缓存 | 无 | 归一化问题+日期 → 5–10 分钟 TTL（重复提问 8s → <50ms） |
| `emu.routing` | 无缓存 | 加当日 TTL 5–10 分钟（担当当日不变） |
| `train.schedule` 经停 | 已有 1h | 保持 |
| `station.screen` | 60s → **已放宽 10 分钟** | 已完成 |
| 启动预热 | `scripts/prewarm.sh` 存在 | 预热高频车次/站点/线路，消灭首问 35s |
| 单工具硬预算 | 无（rail_line 首次 19s 可拖住整体） | 每工具 4s 预算，超时**如实标注**并继续 |

### P3 模型路由（可选，效果中等）

- `LLM_STRUCTURED_MODEL` 目前为空 → 与主模型同款。实测小模型 0.44s vs 1.2–3.3s。
- 另可给分类/抽取设 6–8s 超时 + 换模型重试一次，削掉 9s 的尾部抖动。
- **取舍**：小模型的意图/槽位准确率需要用 R1 测试集回归验证后才敢切（可省 ~1–3s）。

## 四、建议的实施顺序

1. **P0-1 + P0-2 + P0-3**：效果最好、互相补位，建议一起做（1 次改动 + 回归）。
2. **P1-1 + P1-2**：体验改善明显且风险低，建议紧随其后。
3. **P2**：缓存/预热可与上面并行；单工具 4s 预算是**行为变更**（可能出现"某数据源超时"的
   如实说明），实施前需评估该取舍是否可接受。
4. **P3**：建议先不动，等 P0 落地后用 R1 测试集评一次小模型的意图/槽位准确率再决定。
