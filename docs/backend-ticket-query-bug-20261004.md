# 余票查询返回时刻卡片：后端交接报告

## 用户复现

查询“G1 明天的时刻表”后，点击“查余票”，发送“查一下 2026-10-05 G1 的余票”。实际再次返回时刻卡片，没有余票结果，也没有补充区间提示。用户截图日志显示：意图 ticket；槽位 target=G1、time=2026-10-05；快路径 NO_SLOT（命中余票但缺区间）；检索只有 train.schedule:ok；生成后抑制了结构化事实文本。

## 代码依据

- frontend对应的原生客户端 MainChatScreen.kt:suggestedQuery 原先未附带卡片已知起讫站，本轮已修复；缺起讫站时生成含出发站/到达站占位文字的可编辑草稿，不猜实际区间。
- backend/app/pipeline/retrieve.py:_plan 的 ticket 分支，车次目标优先调用 train.schedule；仅有 od 时追加 ticket.query。
- train_schedule.py 成功分支实际可返回 seats；display_result.py 当前没有席别余票投影。因此问题还涉及工具有数据但结构化卡片只展示时刻，需检查本次实际工具数据后区分“不可得”和“未展示”。
- 缺 od 的分支说明“已用 train.schedule 取该车次余票”，不能保证展示协议确实含席别数量。当前截图只有时刻卡，说明余票意图没有得到可见完成或澄清。
- 流式结构化回答保护与展示投影叠加后，补充区间说明未显示；需核查 orchestrator.py 的结构化查询抑制范围及 display_result.py 是否支持余票展示，不应仅关闭重复事实保护。

## 后端待处理范围（本轮未改后端）

1. 明确余票查询必须对应日期及实际乘车区间；有区间时确实调用 ticket.query 并按请求车次过滤结果。
2. 缺区间时返回可见的补充信息请求，或从明确的上下文提取并让用户确认区间；不能将时刻查询视为余票查询成功。
3. 保留工具成功/失败状态及来源，不将票价、时刻或车型替代余票；缺少余票数据时如实说明。
4. 检查结构化文本抑制是否吞掉澄清或业务失败说明，保证前端收到可渲染的信息。

## 后端验收建议

- 原句“查一下 2026-10-05 G1 的余票”缺区间时，应显示补充起讫站提示，不再次只给时刻卡。
- “查一下 2026-10-05 G1 北京南到上海虹桥的余票”应查询对应区间，按 G1 输出席别余票或真实失败原因。
- 区间不同、当天/未来日期、无余票、接口不可用应分别验证；工具请求载荷与最终可见结果一致。

报告仅根据用户截图与代码审查确认；本轮没有实际访问12306余票接口，不宣称线上查询已恢复。
