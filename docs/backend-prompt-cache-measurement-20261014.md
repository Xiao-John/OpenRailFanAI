## 已实现的统计

现有 `GET /api/metrics` 的 `llm[供应商标识].prompt_cache` 新增：

| 字段 | 含义 |
| --- | --- |
| `reported_calls` / `unreported_calls` | 有效报告缓存用量 / 未报告或数据无效的调用数 |
| `hit_calls` | 至少一个输入 token 命中的调用数 |
| `hit_tokens` / `miss_tokens` | 已报告的输入命中 / 未命中 token 累计数 |
| `reported_prompt_tokens` | 上述有效用量覆盖的输入 token 总数 |
| `token_hit_rate` | 累计命中 token ÷ 累计有效输入 token |
| `request_hit_rate` | 命中调用数 ÷ 有效报告调用数 |

无有效分母时返回 `null`。明确报告零命中才计入零命中样本；失败、取消和缺失用量归入未报告计数，不拉低命中率。流式累计用量按一次调用计数，不逐块重复累加。后续累计用量缺少或矛盾的缓存数据时，归为未知，避免使用旧分子配新分母。

支持 Chat Completions 的 `prompt_tokens_details.cached_tokens`、SiliconFlow 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，以及 Responses 的 `input_tokens_details.cached_tokens`。SiliconFlow 字段来源：[官方接口文档](https://docs.siliconflow.cn/docs/api/chat-completions-post)。

统计为单进程启动以来的累计值，重启清零；供应商标识相同的模型会合并统计，比较模型时需使用独立测量进程。指标不保存问题、回答或密钥。本地规则直接完成的请求没有云端用量，不能当作缓存未命中。

## 对低命中率的判断

问题各不相同，并不必然导致低命中：不同问题仍可能共享固定的指令与输出约束。动态历史、检索事实和日期越早出现，可共享的前缀通常越短；这是需要测量的因素，不能直接据此判定供应商命中率。

下一步先恢复有效云端调用，再分别统计决策、知识生成和动态检索生成。以 token 命中比例为主，同时报告有效用量覆盖、未命中输入量与首字延迟；不凭少量重复问题声称达到性能目标。暂不加长提示词，也不修改生产模板来追求数字。
