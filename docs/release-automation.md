# 一份文件驱动 Main 发布

以后每次发布只需准备 `docs/release-<版本>.md`，然后在仓库根目录运行：

```bash
./scripts/release.sh docs/release-0.1.30.md
```

文件首部使用 JSON 注释提供发布元数据，其后正文直接作为 GitHub Release 说明。示例见 [0.1.30](release-0.1.30.md)。下一版复制后修改 `version`、`previous_version`、标题和正文；`previous_version` 对应的正式签名回执必须存在。

脚本执行：

1. 验证 GitHub 写权限、origin、当前分支、版本及默认分支的快进关系。
2. 更新 `VERSION`，提交当前所有未忽略改动；拦截私钥、签名配置、APK及明显真实 GitHub 凭据。**执行即授权发布此工作区内全部未忽略改动，应先整理好范围。** 这不是完整秘密扫描器，`.gitignore` 仍是重要边界。
3. 从干净提交构建包含词典的 Main 正式签名包。
4. 用 `apksigner`、`aapt` 及 APK 内元数据核对签名延续、正式包属性、版本、源码提交、词典；生成 SHA-256 文件。
5. 原子快进推送当前分支、main与版本标签，不使用 force。
6. 创建草稿 Release，上传 APK 与摘要文件，核对 GitHub 返回的大小和 SHA-256 后才公开并标记 latest。
7. 自动生成 `docs/verification/release-<版本>.json`，提交回执并再同步分支。版本标签始终指向实际构建提交，回执提交在其后。

凭据优先使用临时 `GH_TOKEN` / `GITHUB_TOKEN`，否则从 Git credential helper 读取，只在当前进程内使用。不要把 Token、签名密码写入发布文件或脚本。构建沿用本机已配置的签名，不创建新签名。

## 中断与恢复

进度保存在被忽略的 `.ai/releases/v<版本>/state.json`。用同一文件、同一分支重新执行即可，脚本重新检查包和远端资产；公开后绝不覆盖不同摘要的同名资产。已开始的发布说明不应修改，防止同一标签产生两份不同说明或包。

任何失败都返回非零并保留已有状态，不自动撤销提交、删除公开版本或覆盖远端历史。网络超时后若远端实际上已接收资产，重跑会读取远端并比对摘要。同一台机器不要并发发布不同版本；其它开发任务也应暂停写入，避免构建源码漂移。

本脚本不自动运行测试、安装模拟器或宣称视觉验收通过。发布文件中的 `validation` 必须如实填写实际检查范围；APK验证记录不等于完整产品验收。缺少工具链、离线词典、正式签名或 GitHub Release 权限时停止。

本轮运行的发布是普通可见的正式版本，不是预发布。请勿用同一文件把旧版重新设为最新版本。
