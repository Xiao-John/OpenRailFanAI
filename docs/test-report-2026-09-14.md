## 3. 关键发现：5 个系统性缺陷（改一处，分数跳一档）

> 本轮的 21 条“不通过”**不是 21 个独立问题**，而是 **5 个系统性缺陷**在不同用例上的重复表现。按“修复价值”排序如下。

### 🔴 缺陷 1 ★最高优先：「昨天」缺失 → 历史交路永远查不到（A02/A06/I05b/I07b 共 4 条）

**现象**

| 用例 | 问句 | 回答 |
|---|---|---|
| A02 | G1 **昨天**是哪组车 | “没有提供昨天(09-13)的担当车组信息” |
| A06 | CR400BFA5159 **昨天**跑了什么车 | “未能查询到昨日运行情况” |
| I05b | 那**昨天**呢 | 同 A02 |
| I07b | 不对，我问的是**昨天**的 | 同 A02 |

**但数据其实存在**——rail.re 原始接口返回 30 条记录，明确包含：

```json
{"date": "2026-09-13 11:24", "emu_no": "CR400BFA5054", "train_no": "G1"}
```

**根因（已定位到具体代码行）**：`backend/app/dates.py:19-29` 的相对日期表**没有“昨天”这个键**：

```python
_RELATIVE = {
    "大后天": 3, "大前天": -3,
    "后天": 2,   "前天": -2,      # ← 有“前天(-2)”，却独独缺“昨天(-1)”
    "今天": 0,   "今日": 0, "本日": 0,
    "明天": 1,   "明日": 1,
}
```

实测 `normalize_date("昨天")` **返回空串** → 工具回落到“今天” → 只回今日记录 → 模型如实报“没查到”。

**铁证（同一天的数据，换个问法就能拿到）**：

| 问法 | 结果 |
|---|---|
| “G1 **昨天**是哪组车” | ❌ 查不到 |
| “G1 **上周六**呢”（同为 09-13） | ✅ **CR400BFA-5054** 正确给出 |
| 工具直调 `emu.routing(train=G1, date=2026-09-13)` | ✅ **CR400BFA-5054** |
| I03“CR400BFA-5159 昨天…”（**用车组号问**） | ✅ 20 条历史记录，含 09-13 |

→ 结论：**纯属关键词解析漏项，数据与工具都完好**。加一个 `"昨天": -1` 即可修复 A02/A06 两条，并连带修正 I05b/I07b。

### 🔴 缺陷 2 ★：车次类型只认 G/D/C → 普速车次全线不可用（A07/D06/L04/F03 等）

**现象**：K53、1461、Z5 这类普速车次问“谁担当/几点开/趟数”时，工具直接报“**车次号格式不正确**”并失败，回答只能给 0 来源。

**根因**：`backend/app/tools/emu_routing.py:35`

```python
_TRAIN_CODE_RE = re.compile(r"^0?[GDC]\d{1,4}[A-Z]?$", re.I)   # 只接受 G/D/C
```

实测：`G1/D27/C1234` 允许；**`K53/T9/Z5/1461/K507` 全部被拒**。

**而底层能力其实是有的**：

```
train.schedule(K53)  → 车次 K53：北京→沈阳北，发车 22:35，到达 07:00，历时 08:25。余票：advanced_soft_sleeper=4…
train.schedule(1461) → 1461(北京-上海) 相关车次可查
```

→ 结论：**不是数据没有，是入口正则把普速挡在门外**。修复后 A07、D06、L04 可直接转通过，并解锁“普速时刻/余票/经停”这一大块车迷日常需求（须知中国铁路普速车次数量远多于动车）。

### 🔴 缺陷 3 ★：意图「知识型」误判 → 该查站的去查网页（E01★/E06）

**现象（E01 是★核心用例）**：

| 问句 | 系统干了什么 | 结果 |
|---|---|---|
| 上海虹桥的**电报码**是什么 | 判为 `question_type=knowledge` → 走 web.search | 返回上海市政府官网、上海市百科，**没给电报码** |
| 同问，若按 realtime 走 | `station.lookup` + `cnrail.map` | ✅ 秒回 **AOH** |

**根因**：`retrieve.py` 中知识型问题会**整体替换工具计划**改用 web 搜索（原意是避免“样车编号”误查实时工具，见 `plan.md` M10c），而“电报码”这类**看似常识、实则是站点库精确查表**的问题被连带误伤。

**量化**：
- 直查 `station.lookup("上海虹桥")` → `上海虹桥（电报码 AOH，拼音 shanghaihongqiao）`，**又准又快**
- 走网页搜索 → 3 条来源全部无关，E06 同样中招（问苏州站 vs 苏州北站，只回了苏州市概况）

→ 结论：**该用例的能力 100% 具备，被路由策略挡掉了**。建议对“电报码/车站/站名”类关键词强制走 `station.lookup`，不受 question_type 影响。

### 🔴 缺陷 4：地名降级不到位 → 旗舰场景失效（G01★）

**现象**：产品 README 的招牌例句「我在**吉林市船营区**，要拍 CR400AF，今天下午」，实测 `station.lookup` 直接失败，模型因此无法把车型与吉林车次挂上，也给不出机位。

**根因**：`backend/app/tools/_rt12306.py` 的候选词生成只做“截断尾部”，实测：

```
'吉林市船营区' → 候选: ['吉林市船营区', '吉林市船营']     ← 卡在这里就停了
'吉林市'       → 候选: ['吉林市', '吉林']                 ← 若降到这里就能命中
```

**对照**：`station.lookup("吉林市")` → ✅ 正常返回 `吉林（JLL）` 等；`station.lookup("吉林")` → ✅ 正常。**只要多降一级就能成功**。

**连带影响**：E05“重庆主城区”同理失败（直查“重庆”可返回重庆北/西/沙坪坝等）。这条直接影响**产品门面场景**，建议列为与缺陷 1 同级的优先项。

### 🟠 缺陷 5：列车查询缺省日期落进「已发车」分支 → 经停/历时丢失（D02/D03）

**现象**：问「G1 都经停哪些站」「G1 全程多长时间」（**未指定日期**），模型答“无法提供经停站/历时”。**但换个问法（D08「G1次列车明天几点发车」）就能拿到完整的经停与历时**。

**根因**：不带日期时 `train.schedule` 按“今天”查，而 G1 当日 06:30 已发车，返回 `status: "departed"`，且返回体是**15 趟无关车次列表**、`stops=null`：

```json
{"train_code":"G1","status":"departed","count":24,"trains":[G19,G795,G799,…],"stops":null}
   ↑ 用户问的 G1 本身不在 trains 里，也没有经停站字段
```

→ 结论：**“已发车”兜底分支只做了状态提示，没有回退去取该车次的静态时刻/经停**，导致最常用的“这趟车经停哪儿”反而答不上来。建议：已发车时回退查该车次当日的完整站序与历时。
