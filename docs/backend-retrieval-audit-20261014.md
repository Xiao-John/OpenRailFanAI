# 检索流程审计与耗时占比

日期：2026-10-14。范围：Main 后端当前检索代码；本轮仅新增审计记录与文档，未修改生产逻辑、客户端、版本或运行中的服务。

存在可消除的重复取数，优先优化同一区间的票价/余票数据获取，其次处理网页过量抓取与计划重复。当前确定性服务查询的耗时主要在检索；普通云端问答不能沿用这个占比。

## 时间占比

### 当前代码真实查询

本轮在独立进程中执行生产 `orchestrator.run_stream`，日期为 2026-10-15（提问使用“明天”），未替换铁路接口。限定 3 个请求、每个最多 40 秒；仅执行确定性服务入口，阻止云端生成调用。三条请求均正常交付 done，用量均为 0 token。

| 场景 | 检索阶段 | 后端流程总耗时 | 检索占比 | 查询结果边界 |
| --- | ---: | ---: | ---: | --- |
| G1 时刻表 | 1183.2 ms | 1183.4 ms | 99.98% | 时刻工具返回 ok |
| G1 北京南→上海虹桥票价及余票 | 469.1 ms | 469.4 ms | 99.94% | 两个工具均返回 ok |
| G1、G2 同区间票价及余票 | 579.5 ms | 579.7 ms | 99.97% | 四项中 G2 余票失败，其余返回 ok |

`ok` 是工具状态，可能包含空数据，不等于每个车次都有可购车票。第三条是部分查询失败，不能计为全服务成功。按相同方向给 G2 查询是为了审计共同区间取数，本轮没有判定其该日期是否应开行于该区间。

这是 n=1/场景的观测，不是稳定性能基线。依次执行的样本共享本测量进程缓存：第三条的 G1 余票命中前一条快照，约 0.15 ms；票价未复用结果快照。首条是本进程首次调用，不能声称外部服务冷缓存。这里的检索阶段包含工具等待、预取清理和结果投影；总耗时止于后端 done 构造，不包含手机渲染或完整传输。

## 无效与冗余检索

### 1. 票价路径重复获取区间售票列表：优先处理

`executed_fare.query` 每个车次独立执行 `fare.init → fare.rows → fare.execution`。同区间、同日期的两个车次，受控传输复现为 **2 次 init、2 次区间列表、2 次分车票价**；当前真实两车样本也出现两次 `fare.init` 和两次 `fare.rows`。外层共享键包含车次，不能合并不同车次的列表获取。[代码](../backend/app/tools/executed_fare.py)

票价与余票合卡是已授权的产品行为，两个事实均有用途；冗余在底层取数。真实单车联查同时出现 `fare.rows` 与 `tickets.query`，都为同日同区间售票列表，但走独立抓取/解析。余票查询内部也没有复用票价的原始记录。[代码](../backend/app/tools/_rt12306.py)

建议建立请求内的区间原始记录共享层，再分别解析余票、内部车次/区间站序和执行票价。须保留初始化与 Cookie、实际乘车区间、日期、成人/其他用途、完整配置隔离，以及每个车次独立失败。不能直接拿已裁剪的余票结果代替票价所需原始字段。

只计票价路径，若 N 个车次各对应一条记录，共享一次 init/list 后，请求数量可从 `3N` 降为 `N+2`；N=10 时是 30→12。**这是条件成立时的请求数量推算，不是已实现的耗时收益。**

### 2. 网页正文过量抓取：已受控复现

默认保留 2 条成功正文，却并发抓取最多 4 条并等待全部完成。四条均成功的受控样本中，**2 条成功正文被丢弃**；多出的慢请求仍可能延长等待。该策略用于弥补前列页面失败，具有合理目的，但可以分批补抓或达到有效内容目标后结束。[代码](../backend/app/tools/web_search.py)

更明确的无效路径：正文剩余注入预算为 0 时，`max(400, budget // top_n)` 仍使每页至少抓 400 字。本轮受控复现了 4 次这样的抓取，随后生成层的事实截断可能完全排除新增正文。应先判断可用预算，再决定是否抓取。未用该受控数据推算真实网络延迟。

### 3. 计划重复和过宽搜索：已复现，网络重复需分开看

13 个计划探针使用当前 `retrieve`，替换工具传输，不经过模型分类：

- `news + mixed`：已有“近月 + 不限时间”搜索，再追加相同不限时间搜索，3 个步骤中有 1 个完全重复。
- 同时问区间里程与站序：`station.lookup(北京南)` 被加入两次。
- `general + mixed` 且槽位为空：先搜索过宽的“铁路”，再搜完整问题“铁路信号原理”。第一份检索对该问题的针对性不足。

完全同键且重叠执行的调用可以被 registry 在途合并，因此上述重复步骤**不直接等于重复 HTTP 请求**；错开执行或参数不同则不能依赖合并。建议计划先按有效语义键去重，通用搜索优先使用实际问题。资讯的近月/全量两份证据是刻意策略，不能仅因 query 相同就删掉其中一份。

### 4. 等价日期造成快照键分裂：已受控复现

registry 的键虽然单独包含规范日期，却又序列化原始 params。`今天` 与 `2026-10-14` 因此进入不同键。同进程依次执行“今天、当天绝对日期、同一绝对日期”，受控工具实际调用 **2 次**，第三次命中快照。[代码](../backend/app/tools/registry.py)

建议仅规范可明确识别的日期和工具认可的等价参数；未知日期原文、警告语义、查询用途与供应商配置必须保留隔离。本轮证明键分裂存在，未测其线上发生率。

### 5. 标量路由的附带联查：需按用户目的校准

标量 `schedule` 分支对当日 G/D/C 车次附查 `emu.routing`；标量 `emu_routing` 又附查 `train.schedule`。计划探针确认两个方向均存在。明确服务集合入口已只查询请求的操作，二者表现不一致。[代码](../backend/app/pipeline/retrieve.py)

例如只问“G1 今天几点出发”，仍可能经过标量分支取交路；这份事实是否有产品用途需要按回答与卡片消费确认，不能仅凭计数全部删除。未来日期交路已经被过滤，本轮探针没有发起该调用。

标量 schedule 的任意非空 target 还可被送入 `emu.routing(emu_no=...)`；“标杆”探针命中此路径。但交路工具会校验格式并拒绝，**未证明它发出外部请求**。可在计划阶段提前澄清，主要改善无意义失败，而非重大网络收益。

## 保留的必要工作与测量局限

- 余票低余量二次采样是现有校验策略，不应当作普通重复查询删除。优化区间共享时必须允许显式刷新，不能把两次校验合并成同一份快照。
- 时刻查询的官方身份、经停站、区间售票及同车不同号回退服务于不同判断；不可只因车次一致就合并或删除。
- 缺少区间和超出 10 车次的探针均为 0 工具调用；当前限额能阻止这些无效检索。
- 当前三个真实服务样本均未启动投机预取；因此本轮未取得预取浪费率。预取的 started/used/unused 指标仍可用于后续完整请求观察。
- 并发工具耗时不可求和当作用户等待。工具指标还排除了获取执行信号量之前的排队，只有检索墙钟覆盖整体等待。MCP 父操作与 init/query 子操作也不能重复相加。
- 新闻搜索、知识问答、站点、拍车等路径仅做代码与受控审计，未取得本轮真实网络延迟分布；未报告全系统“无效检索率”。

## 后续顺序

1. 请求内共享票价/余票的区间原始记录，先验证单车、十车、多日期、失败与取消；保留执行票价、区间精确绑定及低余量刷新。
2. 规范缓存键、去重计划、正文按有效预算抓取；三者分别测量，避免把收益混在一起。
3. 校准标量分支的附带服务，记录工具结果是否进入最终回答/卡片，确认用途后裁减。
4. 建立当前版本逐请求的决策/检索/生成/排队记录。按直接服务与云端问答分别冻结场景、重复次数和成功口径，再评估 30% 目标。
