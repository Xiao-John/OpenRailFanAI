## 1. 缺陷 1 ★：「昨天」缺失 → 历史交路永远查不到

**现象（4 条不通过 + 1 部分）**：A02「G1 昨天是哪组车」答"没有提供昨天(2026-09-13)的担当车组信息"；
A06、I05b、I07b 同因；A10「上个月15号」虽换算正确但同样落在"查不到"。

**根因（已核实到代码）**：`backend/app/dates.py` 的相对日期表**没有"昨天"这个键**：

```python
_RELATIVE = { "大后天": 3, "大前天": -3, "后天": 2, "前天": -2,
              "今天": 0, "今日": 0, "本日": 0, "明天": 1, "明日": 1 }   # ← 独缺 昨天(-1)
```

`normalize_date("昨天", default_today=False)` 返回空串 → `emu.routing` 的 `date` 参数为空 →
工具 `focus_date` 落回"今天" → 只回今日记录 → 生成层如实报"查不到"。**数据本身存在**
（rail.re 的 30 条记录里第 2 条就是 `2026-09-13 CR400BFA5054 → G1`）。
报告还发现自相矛盾：同一天用「上周六」问却能答对 → 印证是**解析漏项**而非数据问题。

**解决方案（已实施）**：
1. 补齐相对日期：`昨天/昨日/昨晚/昨早 → -1`，`今早/今晨/今晚/今夜 → 0`，`明早/明晚/明夜 → +1`；
   保留"最长匹配优先"（"大前天"不会被"前天"截胡）。
2. 顺带补齐报告建议的同类词：`上周X`（上一周，不能算成本周）、`上个月15号/下月3号/本月20号`。
3. 仍然保留 `date_note()` 的诚实降级：真正无法识别时明确说"已按今天处理"。

**验证**：`test_yesterday_and_relative_dates` / `test_weekday_and_month_dates`
（昨天=09-13、上周六=09-12、上个月15号=08-15 等，全部按当天相对计算）。

**预期效果**：A02/A06/I05b/I07b 由"不通过"转"通过"；A 类通过率会因此显著上跳。

## 2. 缺陷 2 ★：车次类型只认 G/D/C → 普速全线不可用

**现象（3 条不通过）**：A07「K53 今天由哪组车担当」、D06「1461 都经过哪些站」、L04「下周三北京到上海的普速有几趟」。
其中 A07 耗时 **143 秒**（全轮最慢）、0 来源，而底层 `train.schedule(K53)` 其实**能查到**
（北京→沈阳北 22:35 发车）。

**根因（已核实）**：两处正则都只收动车组：
- `emu_routing._TRAIN_CODE_RE = ^0?[GDC]\d{1,4}[A-Z]?$` → `K53/T9/Z5/1461` 被"格式不正确"拒绝；
- `_rt12306._TRAIN_CODE_RE` 同款 → `retrieve` 也不认普速，无法改道。

**解决方案（已实施）**：
1. `_rt12306` 的车次正则放开为 `G/D/C/T/Z/K/Y/S/L/B/N + 纯数字`，并**排除年份形态**（`19xx/20xx`），
   否则 "2026年9月14日" 会被当成"车次 2026"；自由文本扫描仍只认字母前缀 + "1461次" 形态，避免误命中。
2. 新增 `is_emu_train_code()`：只有 G/D/C 才是 rail.re 交路库的覆盖范围。
3. `emu_routing` 对普速**如实说明数据源边界**（而不是"格式不正确/查询失败"）：
   "K53 为普速/非动车组车次，rail.re 交路库不收录其担当信息；时刻/经停请用 train.schedule"。
4. `retrieve`：普速的"担当"意图**改查 `train.schedule`**（实时时刻/经停），并在 note 里说明
   "机车担当无公开数据源"。

**验证**：`test_train_code_covers_conventional`、`test_emu_routing_rejects_conventional_honestly`、
`test_retrieve_conventional_train_routing`。

**遗留（可选增强）**：普速"担当机车"确实无公开源（12306 不公开、rail.re 只收动车组）——
产品上建议在 UI/文档中明确"该能力仅覆盖动车组"，避免用户反复尝试。

## 3. 缺陷 3 ★：知识型误判 → 该查站的去查网页

**现象（E01★ 核心用例）**：「上海虹桥的电报码是什么」被判 `question_type=knowledge`，
`retrieve` **整体替换**工具计划为 `web.search` → 返回上海市政府/百科页面，**没给 AOH**；
E06「苏州站和苏州北站是一回事吗」同样只回了苏州市概况。

**根因（已核实）**：`retrieve.py` 的 M10c 策略是"知识型 → 只走 web 搜索"，
而"电报码/站名/站台"这类**看似常识、实为站点库精确查表**的问题被连带误伤。
直查 `station.lookup("上海虹桥")` 秒回 `AOH`。

**解决方案（已实施）**：
- 新增站名事实词识别（`电报码|电报|拼音码|站名|车站|站台`）；
- 知识型分支不再"整替换"，而是**保留计划中的站点类步骤**（`station.lookup`/`cnrail.map`）+ 追加 web 搜索；
- note 说明"该问题涉及站点事实：已保留站点库精确查询，网页搜索仅作补充"。

**验证**：`test_retrieve_station_fact_forces_lookup`（断言 `station.lookup` 仍在计划里；
同时断言**一般知识型问题仍只走搜索**，不误用实时工具）。

## 4. 缺陷 4 ★：地名降级不到位 → 旗舰句失效

**现象（G01★ 产品门面用例 + E05）**：「我在**吉林市船营区**，要拍 CR400AF，今天下午」
→ `station.lookup` 失败 → 无法把车型与本地车次关联 → 也给不出机位。E05「重庆主城区」同理。

**根因（已核实）**：`_rt12306.station_candidates()` **只剥两轮后缀**：

```
'吉林市船营区' → ['吉林市船营区', '吉林市船营']      ← 卡住，"船营"尾部不是后缀词
'吉林市'       → ['吉林市', '吉林']                ← 能降到这里就能命中
```

**解决方案（已实施）**：
1. 后缀表扩充（区/县/市/省/自治区/自治州/地区/特别行政区/**新区/城区/主城区/市区/街道/镇/乡**）；
2. 改为**逐级剥离直到稳定**，并补"截到行政区级别"的候选（解决"吉林市船营"这类残尾）：
   `吉林市船营区 → 吉林市船营 → 吉林市 → 吉林`；`重庆主城区 → 重庆`。

**验证**：`test_station_candidate_degradation`。
**实测**：`station.lookup("吉林市船营区")` 现在 ✅ 返回 9 个站点（note 注明"已将'吉林市船营区'按'吉林'检索"）。

## 5. 缺陷 5：已发车分支丢失经停/历时

**现象（D02/D03）**：「G1 都经停哪些站」「G1 全程要跑多长时间」（**未指定日期**）→
答"无法提供经停/历时"；而 D08「G1 明天几点发车」却能给出完整经停与 04:54 历时。

**根因（已核实）**：不带日期时按"今天"查，G1 当日 06:30 已发车 → 12306 不再列出 →
工具走 `status: "departed"` 分支，而该分支**只返回状态提示 + 15 趟无关车次**（`stops=null`），
没有回退去取该车次的静态时刻/经停。

**解决方案（已实施）**：已发车分支新增 `_reference_schedule()`：
**查次日同车次**的时刻/历时/经停（12306 对已发车次不列出，而次日同图），
并在正文与 note 中明确标注"**次日参考，调图或临时调整时可能不同**"。

**验证**：`test_departed_train_reference_schedule`（stub 掉 12306，断言取到次日 06:30-11:24、历时 04:54、经停 3 站，
且文案含"参考/调图"）。

**同类建议**：D05「已发车」现状是"如实说明"（通过），本次修复让 D02/D03 也能答出关键信息。

## 6. 次级问题 6：资讯时效不可判 → H02 反向错误（最危险的一条）

**现象**：「沪苏湖高铁开通了吗」答"**尚未开通、正试运行**"，而事实是 **2024-12-26 已开通**。
同一批检索结果里第 1 条恰恰是"正式开通运营"，第 2/4 条是"即将通车"的陈旧条目 —— 模型取了旧的。

**根因**：`web.search` 返回结果**不带日期**，模型无从判断新旧；生成策略里也没有"时效优先"规则。

**解决方案（已实施，两层）**：
1. **证据面**：`web_search` 从标题/摘要/URL 抽取日期（`2024-12-26`、`2024年12月26日`、`12-26`），
   渲染为 `[2024-12-26] 标题`；无日期的显式标 `[日期未知]`；note 报告"相关 N 条，其中 M 条带日期"。
   仅月日时**不臆造年份**（"预计年底开通 12月26日"→ `12-26`），避免模型据此误判新旧。
2. **策略面**：生成 prompt 增加资讯时效规则 —— 以**日期最新**条目为准、无日期不得作为时效依据、
   新旧冲突必须说明并倾向最新、不得仅凭陈旧条目下"尚未开通/已停运"结论。

**验证**：`test_search_result_dates`、`test_news_recency_policy_in_prompt`。

**真实数据实测（2026-09-14）**：用 `web.search("沪苏湖高铁 开通 运营")` 抽验 →
note 报"相关 4 条，其中 **0 条带日期**"（百度/必应标题普遍不带日期）。
不过本次返回的条目本身已能说明状态（"沪苏湖高铁开通运营'满月'"），
配合新增的时效规则应能给出正确结论。

**仍是风险与后续方案**：
1. 若某次检索的日期**全都缺失**且条目新旧混杂，模型只能依赖"不绝对化 + 说明冲突"这条规则；
2. 建议下一步：`news` 意图加**时效过滤**（如必应 `filters=ex1:"ez3"` 近一月）或**优先官方源**
   （12306 公告、国铁集团官网），并对"开通/停运/调图"类问题**强制要求带日期证据**才能下确定结论。
   本次未实施，避免只为单个用例过拟合（过滤近一月会顺带滤掉权威旧闻）。

## 7. 其他独立问题（逐条）

### 7.1 C04/C09：车次席别问题走错工具 ✅ 已修
**现象**：「G1 明天还有商务座吗」→ 无区间可析 → 只做 `station.lookup("G1")` 且失败 → 0 来源（直查可得 business=16）。
**根因**：`retrieve` 的 ticket 分支在缺区间时只查站点。
**修复**：ticket 意图且目标为**车次号** → 改走 `train.schedule`（直接取该车次席别），并说明"区间余票需要出发站与到达站"。
**验证**：`test_retrieve_ticket_with_train_code`。

### 7.2 A09/A09b：「京沪标杆」被当车组号 ✅ 已修
**现象**：重复 2 次都 0 来源，回答只说"工具调用失败"。
**根因**：目标既不是车次号也不是车组号，却被塞进 `emu.routing(emu_no=...)`。
**修复**：`retrieve` 先判断目标形态 —— 是车组号才查交路；否则走检索并说明"请提供具体车次（如 G1）"。
**验证**：`test_retrieve_non_code_target_is_honest`。

### 7.3 C06/C08/L03/D09：把"没查"说成"查询失败" ✅ 已修（口径）
**现象**：C06「未发起余票查询」被写成"ticket.query 调用失败"；C08/L03 实际是**超预售期**；
D09 缺出发站却答"数据源调用失败"。
**修复**：
- `retrieve` 引入 `plan_notes`：**没发起的查询要说明缺什么**（缺到达站/缺出发站/未识别区间），并入最终 note；
- `ticket.query` 新增 `_presale_hint()`：日期超出 `TICKET_PRESALE_DAYS`（默认 15）时，
  在 note 中写明"属正常查不到而非系统故障，请在开售后再查"。

**验证**：`test_retrieve_missing_info_notes`、`test_presale_hint`。

### 7.4 F07：「北京到北京」退化成网页搜索 ✅ 已修
**根因**：`parse_od()` 在 `f == t` 时返回 None（视同解析失败）→ 计划落空 → 整句去搜索（命中"中国/政府网"）。
**修复**：同站对如实返回，交由 `rail.line` 给出明确结论（该工具本就有"发站与到站相同"的提示）；
同时 rail_line 的失败 note 不再推荐"实测无效的电报码"写法。
**验证**：`test_same_station_od`。

### 7.5 E07：错别字无纠错动作 ✅ 已修（能力边界内）
**现象**：「太安站」未纠正为泰安，也未给候选站（未编数据，但纠错动作缺失）。
**修复（两条腿）**：
1. 站点查询失败时给出**候选站列表 + "若为同音字（如'太安'→'泰安'）请核对"** 的提示
   （排序按首字/末字/长度重合度打分 —— 实测 difflib 对中文同音字无效，已弃用）；
2. 生成策略新增**唯一例外条款**：站点未命中时允许模型基于自身知识指出同音/形近站名，
   但必须标注"（据模型知识，未检索确认）"。
**验证**：`test_station_lookup_suggests_alternatives`。
**遗留**：要让工具自己就能给出"泰安"，需要中文拼音能力（如 `pypinyin`）—— 属新增依赖，**需单独评估**是否引入。

### 7.6 K07：城市交通被误判 ✅ 已修（口径）
**现象**：「从上海怎么去迪士尼」被判 `rail_line` → 检索误命中"中国/政府网" → 答"没找到"。
**修复**：意图 prompt 补 2 条 few-shot（迪士尼/机场交通 → `general`+`knowledge`）与判定要点
（"与铁路无关的城市交通/出行方式不要判成 rail_line 或 ticket"）。
**验证**：`test_urban_transit_intent_examples`。
**说明**：意图分类是 LLM 判定，few-shot 能显著降低误判但非 100% 确定；后续可用"线路意图但无有效区间 → 改常识作答"的兜底再加固。
