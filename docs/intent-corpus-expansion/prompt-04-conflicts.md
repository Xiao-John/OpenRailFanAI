# C：冲突、反例与动作语料提示词

请生成 OpenRailFanAI 新决策树的困难候选，重点验证错误接管风险。批次 C 目标 100 条。

先读 AGENTS.md、docs/ui-design-boundaries.md、docs/backend-parallel-development-boundaries.md、docs/intent-corpus-expansion/CONTRACT.md 和本提示词。不要读实现、旧 SPEC、旧语料、测试、其他批次或旧树；不联网。只写 `.ai/intent-corpus-v1/C/`，目录已有产物则另建 C-run2。

覆盖以下场景，不能只堆“为什么”或无意义长句：

- 线路沿线车站 vs 单站信息 vs 车次经停；拍摄目标里的车型/担当词 vs 真正的交路主诉求。
- 余票 vs 价格；图定时刻 vs 实际到点、晚点和位置。
- 车型/车组/日期/钟点/数字车次的边界，真实站名与普通词同形。
- 多车次、多日期、多区间、多独立诉求、知识与实时混合；否定、比较和明确更正。
- 铁路“客车”语境 vs 公路客车，车站问路 vs 景点交通，机票 vs 火车票。
- 多段行程和中转；明确需求但当前执行能力未确认。
- 结构化动作与文本/历史冲突，以及少量未知/非法动作载荷。

建议 70 条文本困难样本、20 条既有动作样本、10 条无效/长输入；至少 20 组最小对照，计入总数。合法动作只用 CONTRACT 允许的现有 kind，不新增客户端字段。未知/非法动作可以构造，但不能强行制定 HTTP 状态、失败文案或恢复行为。

多诉求全部保留，不能把 G1/G2 或担当/经停只保留第一项。比较句保留两个对象。单个多对象任务与多个独立任务分别标记。真正无法消歧的输入写候选解释和澄清点；只是需要外部事实的输入不要误标为语义 ambiguous。

每条 must_not 至少说明一个具体错误，如“将实际到点答成图定”“把组号数字当车次”“用历史日期冒充查询日”“按按钮文案扩大重试对象”。不要用泛泛的“不能错”。不填写事实答案或完整查询结果。

输出完整 `candidates.jsonl`（ID=C-0001…）、仅输入字段的 `inputs.jsonl`、`manifest.json`、`summary.md`。检查 JSON、ID、来源证据、任务对象是否完整。合法/非法动作的解释须区分语义期望与待定执行政策；使用 eligibility=undetermined/policy_undetermined 记录未定政策，不猜当前代码行为。

manifest 记录 SHA-256、组数、操作/错误风险/eligibility/status 分布。结果仍是候选；不改任何程序、接口、原语料或已有报告。
