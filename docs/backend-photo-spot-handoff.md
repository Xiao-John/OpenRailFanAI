# 机位本地库 · 后端交接

> 一句话：机位**不做实时检索**，改为**离线建库 + 线上零延迟查表**（与 `rail.mileage` 同构）。
> 线上只读本地 `dict.db`，不联网、不花额度、不受反爬影响。

## 1. 为什么不能实时查

机位**没有结构化数据源**，且网页版搜索引擎对批量取数会反爬：

| 事实 | 实测依据 |
|---|---|
| 无结构化源 | OSM 全中国真机位词仅 **3** 个；12306 / rail.re / 黄河铁路网 / GTFS 均无此字段；唯一的车迷机位站 `chinaonrails.org` 已下线 |
| 网页版反爬 | 百度约 70 次检索即返回**图形验证码**；Bing 返回**退化结果**（查"成昆铁路"回汉字「成」的字典词条） |
| 裸地名搜索无效 | `吉林市 铁路拍摄 机位` → 吉林市百度百科；`北京南站 拍车机位` → 北京旅游攻略。**且工具仍返回 `ok=True`、"相关 5 条"**，把无关内容冒充成机位答案 |

## 3. 数据

`backend/data/dict.db`（**gitignored**）新增两表：

- `photo_spot_doc` —— 一行 = 一篇机位攻略。关键列：`scope`（地点）、`title`、`url`、
  `page_text`（**正文原文**，给生成层读）、`entities`、`reasons`（判定依据，可复核）、
  `content_hash`（去重）
- `photo_spot_seed` —— 已跑过的发现查询 + 命中数（可续跑、可算覆盖率）

**现状：810 篇 / 265 地点 / 正文 107.6 万字**（省会 31 个中 30 个 ≥3 篇）。
重建：`python3 scripts/build_photo_spots.py --help`。

## 4. 线上行为（改这里之前先读）

`photo.spot` 的查表口径：`scope ∪ entities ∪ 标题 ∪ **正文**`，排序按相关度
（`scope` 精确 > 标题命中 > `scope` 包含 > 正文命中）。

两个刻意的设计：

1. **必须匹配正文** —— 克俭公园/老道口桥/飞虹路这类小地点**从不出现在 scope 或标题里**，
   只在正文中。只匹配 scope 会让"克俭公园怎么拍车"查不到，而那正是最该答上的问题。
2. **未收录一律 `ok=False`**，note 里明确"不得据此编造点位"。
   宁可说"公开攻略稀少"，也不编。

## 5. 建库怎么跑

```bash
cd backend && PYTHONPATH=. .venv/bin/python ../scripts/build_photo_spots.py --help
```

| 参数 | 用途 |
|---|---|
| `--engine aliyun --aliyun-engine lite` | 取数通道（`lite` ¥8/1000 最便宜；`global_basic` ¥12） |
| `--shapes base,type,roundup,national` | 查询形态；**`national`（全国盘点）产出最高** |
| `--urls urls.txt` | 人工喂链接（每行 `<url> [\| 地点]`），零反爬风险 |
| `--ingest-json x.json` | 吃检索结果（含正文），**不抓网页** |
| `--dedup` / `--rescan` | 清理重复 / **用当前规则重扫存量并删除不合格条目** |
| `--dump-json f.json` | 原始结果落盘 → 规则迭代时可**离线复判，不再花额度** |

### ⚠️ 改闸门规则后**必须**跑 `--rescan`

闸门是在真实数据上迭代出来的，**每次改进都意味着存量里可能已有不合格条目**。
只对新数据生效的话，库里会长期残留旧规则放行的噪声（实测修完同形词后，
存量里那 16 篇汽车拍卖内容仍在）。`--rescan` 只读标题+正文重跑判定，**不联网、不花额度**。

## 6. 闸门三道（`_judge`）

1. **标题必须指明拍摄地点**（机位/拍车点/约拍/拍照…）
2. **标题必须是铁路题材** —— 车迷专用词（拍车/拍火车/看车/摄铁）即通过；
   泛化词（机位/拍照）则需另有铁路词或**本地线路名**佐证
3. **区分"在哪里拍"与"拍了哪趟车"** —— 标题有车次/车组号却无地点类词 → 判为运转视频

## 7. 踩过的坑（别重犯）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **摘要是查询的回声** | 查"福州 拍火车机位"时，旅游文的摘要里就带"拍火车机位"，靠"车迷词命中"被放行 | 意图判定**只看标题**，摘要不可作证据 |
| **站名 ≠ 题材证据** | "上海""秦皇岛"本身就是站名库里的站名 → 迪士尼/阿那亚类内容被判成铁路题材 | 题材证据用**车迷词/铁路词/线路名**；站名只作**地点**证据 |
| **"拍车"是同形词子串** | "**法拍车**""**天天拍车**"是汽车拍卖业务，靠子串命中混入 | `(?<![法天])拍车` 否定后顾 + 标题黑名单 |
| **`_RAIL_FORM_RE` 含裸词"铁路"** | "南昌**铁路**""中国**铁路**"是题材词不是地点词，拿来当地点证据会全放行 | 单列 `_LANDMARK_FORM_RE` 只放地点形态词（道口/立交桥/机务段…） |
| 过度过滤 | 修运转视频时误杀《…五泉南路**立交桥**拍车》《…通过西**机务段路道口**》 | 地标形态词**就是**"在哪里"，必须算地点证据 |
| **正文没在内部传递** | `Finder.run()` 漏传 `prefetched_text` → 一律回退抓网页 → JS 页全丢（初判 337 篇只入库 2 篇） | 搜索接口自带正文必须传到底，否则等于白接 |
| 并发写同一个 db | 两个批次并行写同一 SQLite | 串行，或各用独立库后合并（本次未损坏，但属不必要风险） |
| 额度用尽 | 用户关闭"自动转付费"后返回 403 | 按错误码 `Retrieval.PackageExhausted` 判定并**中止整轮**（否则剩余查询全 403 空跑） |

## 9. 容量天花板（对照 [`photo-spot-db-scale-estimate.md`](photo-spot-db-scale-estimate.md)）

那份文档独立估算了中国机位总量，可作为本库的**容量规划基准**：

| 档位 | 估算数量 |
|---|---|
| 起始收录（**公开可考、有名字**的社区机位） | **2,000～5,000** |
| 核心库（被认可、有稳定拍摄价值） | **约 10,000**（8k～15k） |
| 全量可拍点（含野外分散、无人收录） | 30,000～60,000 |

**当前库的位置**：265 个地点 / 810 篇 —— 落在"公开可考"档的下沿。

两点推论，对判断后续投入很重要：

1. **"饱和"不等于"数据不存在"**：本轮各发现轴都挖到 0.05–0.13 新增/查询，
   但按上表，仅"公开可考"档就还有 2,000+ 的余量。**限制在发现源，不在数据量**。
2. **810 篇 ≠ 810 个机位**：一篇盘点常含多个机位（如《上海8大拍车机位指南》）。
   库里存的是**文档**，不是结构化点位 —— 所以本表不能直接按篇数折算覆盖率。
   若要按"机位"计数，需要做结构化抽取（当前**刻意不做**，见 §8）。

> 若将来改做结构化抽取，`photo_spot_doc` 需扩字段（机位类型/线路/车站/坐标/
> 可达方式/安全提示/拍摄方向/来源），该估算建议按 **10⁴–10⁵ 条**预留，不必按百万级设计。
