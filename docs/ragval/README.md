# RailFanAI · RAG 验证工作流（Agent 交叉验证版）

> **一句话**：把车迷日常问题编成 **机器可读的测试集**（`docs/ragval/testset.txt`），
> 由**多个 Agent 分工执行**——跑用例采集证据 → 主判官评分 → 交叉复核判官独立复评 →
> 外部核证 Agent 对权威数据 → 汇总出通过率与红线段问题，全程**自动交叉验证**，不做人肉手测。

**配套文件**：测试集 [`docs/ragval/testset.txt`](./testset.txt)（50 条）；本文档 = 格式声明 + 工作流 + 评分算法。
**适用对象**：执行/评分/复核/核证等所有 Agent（以及想看懂评分口径的人）。

---

## 0. 为什么要改成 Agent 交叉验证（不再用旧手测清单）

旧版 `docs/testset.md` 是**给人手测**的清单（点开页面、逐条对答案、手动登记），适合人工验收，
但有两个固有弱点这版要改掉：

| 弱点（旧式手测） | 本版（Agent 交叉验证）的处理 |
|---|---|
| 判定主观、"会不会放水"不可控 | 每条用例带**硬性可核对判定点** + **一票否决**；多个判官**独立**评分再交叉比对 |
| 一次只能测一轮，复现差 | 用例是**行式数据**，执行 Agent 逐条打 `/api/chat`，证据落 `evidence.jsonl`，可重复回放 |
| 回答对了没，人说了算 | 正确性由**外部核证 Agent** 拿权威源（rail.re / 12306 / 客里表）对真实数据核对，不靠人记忆 |
| 无法定位是"检索差"还是"生成差" | 按 RAG 分解：分别评 **检索充分性 / 事实忠实度 / 作答相关性**，回归能定位到哪一层 |

## 1. 成熟方案调研（作为本设计的依据）

在动手前对主流 RAG 评估方案做了调研，本工作流**借鉴但不照搬**，取舍如下：

| 来源 / 框架 | 核心思想 | 本工作流借鉴点 |
|---|---|---|
| **RAGAS**：faithfulness / answer relevancy / context precision / context recall | 把"回答好不好"拆成"检索到的上下文好不好 + 回答是否忠实于上下文"两步 | 对齐其"**忠实度**（回答断言是否都被检索事实支撑）"与"**检索质量**（是否取到/用到该取的事实）"两个维度 |
| **TruLens**：groundedness + OpenTelemetry tracing + 阶段 feedback | 评估与可观测绑定，逐环节打反馈分 | 把工具调用轨迹 `tool_trace` 当作"上下文"，逐条核对该上下文是否真的支撑了回答（groundedness） |
| **DeepEval**：RAG 当测试、CI/CD gate、metric-as-assertion、支持 multi-turn | 把评估变成"断言 + 阈值"，回归即失败 | 本设计按维度给 0–1 锚点 + 通过阈值，作为每次改版的 **回归闸门**；多轮用例进测试集 |
| **LLM-as-a-judge + 多判官一致性**（self-consistency / Cohen's κ）：避免单一判官的主观偏置 | 两个（及以上）判官独立评分，不一致时对冲突判别裁决 | 本设计核心：**主判官 + 独立交叉复核判官**，用一致性系数衡量是否可采信，冲突交由裁决环节 |

> 重要区分说明：本项目并不是传统"向量检索 + 分段上下文"的 RAG，而是**工具调用型 RAG**——
> 检索层按意图路由数据源工具（rail.re / 12306 / 径路等），工具返回的 `tool_result` 就是"上下文"。
> 因此本工作流把 **`tool_trace` 当作检索上下文**来评忠实度与检索质量，这比套用向量 RAG 指标更贴合本系统。

**引用来源**（外部数据，仅作方法参考）：
- RAGAS 官方指标说明：<https://docs.ragas.io/en/stable/concepts/metrics/available_metrics> · 仓库 <https://github.com/vibrantlabsai/ragas>
- TruLens（groundedness / tracing / feedback）：<https://github.com/truera/trulens>
- DeepEval RAG Evaluation / CI/CD / multi-turn：<https://deepeval.com/guides/guides-rag-evaluation>
- LLM-as-a-judge 与人工评分对照、多评测一致性：DOI <https://doi.org/10.1186/s40536-026-00287-w>
- RAG 评估框架综述（RAGAS/TruLens/DeepEval 差异）：<https://www.dio.me/en/articles/frameworks-de-avaliacao-de-rag-o-que-muda-no-release-01a46638b003>

## 2. 测试集格式声明（`testset.txt`）

### 2.1 文件规则

- **编码** UTF-8，一行一个用例，`#` 开头为注释/头部说明（执行 Agent 读取时跳过）。
- **字段分隔**：竖线 `|`（用例内自然语言不放 `|`）。
- **多轮用例**：`我要问的话` 列内用 `;;` 分隔每一轮；第二轮起作为上文传入 `history`。
- **判定点、一票否决、来源** 等字段内用逗号 `,` 分隔多项；数值区间如 `1318-1325` 不含逗号，不受影响。

### 2.2 每行九列

| 列序 | 列名 | 说明 |
|---|---|---|
| 1 | **编号** | 分类字母+两位序号（`A01`…）；`★` 缀于编号后 = **核心必测**（改版前后各测一轮对比回归） |
| 2 | **分类** | `A`交路担当 `C`余票 `D`时刻经停 `E`车站 `F`径路里程 `B`车型知识 `G`拍车 `H`资讯 `I`多轮 `K`老实安全 |
| 3 | **模式** | `real`=依赖实时数据/境内网络；`offline`=纯知识/流程；`hybrid`=混合口径。`offline/hybrid` 可在无实时数据时测 |
| 4 | **我要问的话** | 车迷口语原话（可黑话/错字）；多轮用 `;;` 分隔 |
| 5 | **我期待的结果** | 一句话"合格回答"该长什么样（给判官判定 intent 与口径用） |
| 6 | **判定点**（硬性可核对） | 逗号分隔的客观断言：数值/格式/日期锚/站名/行为/口径，判官逐条核对，**全部满足才算该维满分** |
| 7 | **一票否决** | 命中任一项 → 该用例**直接 0 分**并计入红线；需两判官独立确认 |
| 8 | **权威核对源** | `rail.re` / `12306` / `黄河客里表` / `知识`(模型知识,须标注`未检索确认`) / `web` / `工具链`(须与 tool_trace 自洽) |
| 9 | **备注** | 前提、锚点要求、测法约束（如"记下提问时刻""安排在下午"） |

### 2.3 用例规模与覆盖

- 共 50 条，`★` 核心 10 条（A01/A02/A03/C01/D01/E01/F01/G01/I01/K01，覆盖交路招牌、余票、时刻、车站、径路、拍车、多轮、红线）。
- 覆盖：A交路担当 7、C余票 6、D时刻经停 6、E车站 5、F径路里程 5、B车型知识 5、G拍车 4、H资讯 2、I多轮 5、K老实安全 5。
- 红线/老实类（K01-K05）与招牌类（A01-A03）**每轮全测**；其余按轮次抽测并登记抽了哪些编号。

## 3. 运行前置条件

1. 后端以**真实模式**启动（配好 `.env` 的 `LLM_BASE_URL`/`LLM_API_KEY`，`LLM_MOCK=false`），
   运行在**中国境内网络**（rail.re / 12306 实时接口仅境内可达）。启动方式见 `docs/run.md` §4。
2. `offline` 用例可单独对知识/流程做体检，不依赖实时源。
3. 执行 Agent 记录**提问时刻**；实时用例同轮同一时段跑完（间隔 ≤1 分钟）便于与 12306 对表。

## 4. Agent 交叉验证工作流（五个角色，谁负责什么）

数据流简图：

```
testset.txt ──▶ [执行 Agent] ──▶ evidence.jsonl ──┬─▶ [主判官] ──▶ scores.jsonl
                                  ▲               ├─▶ [交叉复核判官]（独立复评）──▶ 一致性
                                  │               └─▶ [外部核证 Agent] ──▶ 权威ground truth
                          ────────┴──────────────▶
                                    │
                    [汇总 Agent]（合并三维度/红线/一致性 → 生成报告）
```

| 角色 | 职责 | 输入 | 输出 |
|---|---|---|---|
| **执行（Runner）Agent** | 逐条读 `testset.txt`，调用 `POST /api/chat`（单轮空 history；多轮把前几轮压进 `history`），把完整返回原样落证据 | 测试集 + 后端 | `evidence.jsonl`（每条含 intent/slots/answer/thinking/sources/**tool_trace**/elapsed/asked_at） |
| **外部核证（Verifier）Agent** | 对每条用例，按"权威核对源"去**外部对照真实数据**（rail.re / 12306 / 客里表 / 公开资讯），产出该条**权威 ground truth**；并核验 tool_trace 是否与外部一致。12306 需境内+反爬支持，属 best-effort，抓不到时退化为以该时刻 tool_trace 为快照真值并在证据里标注 | `evidence.jsonl` + 权威源 | `authority.jsonl`（每条：权威关键值 + 与 tool_trace 是否一致 + 口径标注） |
| **主判官（Primary Judge）Agent** | 按 §6 评分算法逐条打分：正确性(对照 authority 的判定点)、忠实度(回答断言 vs tool_trace)、检索充分性(应调工具是否调对)、作答相关性(intent/承接)、诚实标注 | 证据 + 权威真值 | `scores.jsonl`（每维 0–1 + 合成 + PASS/部分/FAIL + 否决） |
| **交叉复核判官（Cross-Check Judge）Agent** | **看不到主判官结果**，独立按同一算法复评（至少覆盖：全部 ★ + 全部红线段 + 主判官判"部分/失败/否决"的用例；其余抽 1/3），产出独立判定，用于算一致性 | 证据 + 权威真值 | `scores_cross.jsonl` |
| **汇总（Report）Agent** | 合并两个判官结果，算一致性系数 κ 与红线命中；裁决冲突；生成 | 两个得分档 + 权威 | `report`（通过率/分类/维度均值/红线清单/回归对比） |

**一致性裁决规则**：
- 对每个用例，计算主判官与交叉判官在"PASS/部分/FAIL"与"是否命中否决"上是否一致；
- 一致率 ≥ 0.8 且否决命中完全一致 → 结果可采信；
- 否则对发生分歧的用例，由**第三判官（或汇总 Agent 自行复核）**重判一次做多数决；仍分歧则标记为"待人工复核"并单独列出。

> 交叉验证的意义：车迷最恨的就是**编数据**（车次/车组/站名/时刻）。凡命中"一票否决"的用例，
> 一律要求**两个判官都独立判出否决**才计入红线，避免单一判官误判/漏判。

## 5. 数据文件约定

统一放 `docs/ragval/run/`（证据与得分逐条追加，便于回放与回归对比）：

| 文件 | 行格式 | 用途 |
|---|---|---|
| `evidence.jsonl` | `{"id","asked_at","message","history_len","intent","question_type","slots","answer","sources","tool_trace","elapsed","error"}` | 原始问答证据（对齐 `docs/_run_harness.py` 字段并补 `tool_trace`） |
| `authority.jsonl` | `{"id","source","ground_truth","tool_trace_consistent","note"}` | 外部核证的权威真值 |
| `scores.jsonl` / `scores_cross.jsonl` | `{"id","cor","grd","ret","rel","hon","score","verdict","veto"}` | 两判官逐条得分 |
| `report.md` | 汇总结论 | 当轮质检报告 |

## 6. 评分算法

### 6.1 单个用例：五个维度，各 0–1，有锚点

判定原则：**能用权威真值硬核对的就硬核对**（不靠判官感觉）；判官的判断集中在"忠实度/检索/口径"这类需要读上下文的维度。

| 维度 | 简称 | 定义 | 0–1 锚点 |
|---|---|---|---|
| **正确性**（任务成功） | `cor` | 用 `authority.jsonl` 里的**权威判定点**逐条对照答案：满足条数/总判定点数。硬吻合，防"感觉对了" | 全部判定点满足且无误导=1；每缺/错一条按占比扣；含误导性错误即判 0 |
| **事实忠实度**（groundedness） | `grd` | 抽出答案中的**原子断言**，逐个检查是否被本次 `tool_trace` 返回的事实支撑；不支撑且无 `未检索确认` 标注 = 幻觉 | 全部断言被支撑=1；`支撑/(支撑+不支撑)`=该值；含未经标注幻觉则≤0.5 |
| **检索充分性** | `ret` | 该分类**应该调用的工具**是否被调用并拿到可用事实（对应 DeepEval/RAGAS 的 "context 是否取到"代理指标） | 应调工具全调且返回可用=1；调了但事实不可用=0.5；未调用该工具=0（除非知识型/offline 本就不需要检索） |
| **作答相关性** | `rel` | intent 分类对不对 + 是否答了所问 + 多轮指代是否承接正确 + 不答非所问还不吭声 | 全对=1；答对但有绕远/反问废话=0.6；答非所问=0 |
| **诚实与口径标注** | `hon` | 缺数据是否坦白（"没查到/已发车/超出预售期"）；知识型是否带 `据模型知识，未检索确认`；是否附来源；实时/知识口径是否分开不串味 | 口子齐+来源齐=1；有标注但缺口=0.6；该标注未标注=0.4；编造成分存在→见否决 |

**一票否决（红线）**：命中测试集 `一票否决` 列的任一情形（编车次/编车组/编站/编时刻/编里程/推荐危险或违法操作/无响应崩溃）→ 该用例 **单维全 0、合成 0 分、verdict=否决**。

**合成分**（权重合计 1.0，偏重"事实正确 + 忠实"）：
```
score = 100 × ( 0.30·cor + 0.25·grd + 0.20·ret + 0.10·rel + 0.15·hon )
```
（含否决则 `score = 0` 且否决标志置 1。）

### 6.2 单用例判定档

| 档 | 条件 |
|---|---|
| **通过 (PASS)** | 未命中否决 且 `score ≥ 80` |
| **部分通过 (PARTIAL)** | 未命中否决 且 `60 ≤ score < 80`（不计入通过率，但现象必须写进问题清单） |
| **不通过 (FAIL)** | `score < 60`，或命中否决（否决类单独列"红线"） |

### 6.3 整轮聚合指标

```
通过率  = PASS / (PASS + PARTIAL + FAIL)          # 不含否决也计入分母或分开披露，报告中两口径都给
红线命中 = 命中否决的用例数（逐条列出编号与现象）
分类通过率 = 每分类的 PASS 数 / 该分类总数
维度均值 = 全轮 cor/grd/ret/rel/hon 的平均（用于定位：是检索差还是生成差）
判官一致性 = 两个判官在 PASS/部分/FAIL 上的简单一致率 + Cohen's κ（否决是否一致单独披露）
```

**回归闸门（改版用）**：与上一轮对比（
核心★ 10 条全 PASS 且无红线且通过率 ≥ 0.80 视为本轮达标；任一红线或与上轮对不齐即回归失败）。

### 6.4 报告结构（Report Agent 输出，`report.md`）

1. 执行概况（模式/提问时刻区间/用例数）
2. 总通过率 + 三个口径（全部 / 去否决 / 分类）
3. 五个维度均值与**降维定位**（例："grd 0.46 → 回答常见幻觉，优先修生成层"）
4. 红线清单（编号+现象+两判官各自判定）
5. 分类明细 + 未通过/部分通过逐条（编号+哪维丢分+现场）
6. 判官一致性 + 待复核项
7. 与上一轮对比与建议

## 7. 可复现性与数据快照

- **时间锚**：执行 Agent 在 `asked_at` 记下提问时刻；实时用例"今天/明天"都以**该时刻的日历**为准；"明天/后天/大后天"换算由外部核证与判官各算一遍比对。
- **快照语义**：实时数据是"提问那一刻的瞬时值"（12306 也会随分钟变化）；证据里保留该时刻的 tool_trace 作为该时刻 ground truth，判官明确"数据是我那一刻的快照"。
- **重跑**：同一 `testset.txt` 逐条重放即得新证据 → 新得分 → 与旧报告对比，即可做回归。
- **来源留痕**：每条证据保留 `sources`，报告中保留权威源链接与检索日期，满足"发现留痕、数字不自相矛盾"的仓库约定。

## 8. 谁触发 / 如何执行

- **触发者**:此验证工作流由 **Agent**（本会话即执行/裁决角色）在拿到运行中的后端后执行，
  人工只需:① 按 `docs/run.md` §4 以真实模式启动后端;② 确认在境内网络;③ 阅读报告中列出的待复核项。
- 一次完整轮：执行 → 外部核证 → 主判官 → 交叉复核 → 汇总，五步可串成一轮自动质检。
