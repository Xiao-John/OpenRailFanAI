## 首次使用理解成本

“想查哪趟列车？”以及查票价、查时刻、查交路、找机位四个入口，可以让有列车查询需求的人迅速理解用途。“点选示例后可修改，再发送查询”明确了点击不会立即请求；本次点击查票价后，输入框确实填入“明天北京南到上海虹桥的 G1 票价”，打开键盘，发送仍由用户决定。这一步的学习成本较低。

模型配置的理解成本明显高于查询入口。初始空对话没有当前模型是否可用的文字状态；设置页尚未添加提供商。直接问票价会返回有效数据，同时又出现模型不可用及密钥无效提示。用户需要自行理解“有答案但模型失败”的关系，才知道是否必须去设置。初始输入提示仍是“继续追问…”，对尚未问过问题的状态略有歧义。

## 导航、触控与排布

本次成功通过顶栏进入设置、历史和新对话。历史抽屉提供搜索、新建、按“今天/更早”分组的会话，以及各会话的更多操作；改名后搜索“盲测”只显示相应会话，重命名可立即用于辨认测试记录。删除确认层明确给出会话名和“该操作不可恢复”，取消后会话保留。

所采样的完整可见交互区域较宽裕：顶栏三个按钮都是 126×126 px，约 48×48 dp；查询按钮也是 48×48 dp；空对话示例为 446×147 px，约 170×56 dp；设置中的保存、返回、测试连接及获取模型的高度均为 126 px，约 48 dp。没有在这些完整可见区域中发现低于 44 dp 的触控目标。滑动过程中的部分裁切边界不能用作按钮设计尺寸，因此未把它们当成触控不足证据。

键盘打开后，输入框从 `[81,2138][843,2264]` 移到 `[81,1363][843,1489]`，查询区域随之上移。本次能输入、发送、关闭键盘；所测状态没有发现输入框落入系统导航栏的证据。原有留白不作为问题。

## 反馈、阅读与输入

设置页对缺少字段显示“请先填写接口地址、API Key 和模型”；本机地址测试失败显示“连接失败，请检查网络、密钥及接口地址后重试”，获取模型失败也在同一页面给出文字反馈。保存完整的虚构设置后返回原对话。生成时曾实际观察到“正在查询列车数据…”、已识别 G1、停止生成按钮及“可停止生成，已返回内容会保留”，但没有点击停止验证其结果。

时刻结果比纯文本降级回复更便于扫读：车次、方向、日期、历时、车站、到达/出发时间分别出现，站名下有停站分钟数；实际读到七个站。卡片底部有来源、“图定时刻不代表实际正晚点”，详情中有数据日期、时间口径和查询耗时。滚动后有回到底部入口，点击后该入口消失。复制、重新生成按钮可发现，但未验证剪贴板结果或重新生成的成功路径。

主要摩擦集中在失败解释、草稿保护和降级内容的组织上，详见以下问题。

## 问题（按严重度排序）

严重度含义：P1 为阻断主要任务或重大数据损失；P2 为会显著增加操作成本、误导行动或造成局部内容损失；P3 为可继续使用但容易产生困惑。此次未验证到 P1。

### 1. P2：失败被错误地归因为“密钥无效”

**状态：已验证。**

复现：① 在初始未添加提供商的状态发送票价示例；② 观察结果下方的错误区域；③ 再配置本机地址 `http://127.0.0.1:1/v1` 和虚构密钥，保存，点击重试；④ 展开错误详情。

证据：初始未填写任何密钥就显示“暂时无法连接模型服务”、固定遮蔽的 API Key 和“密钥无效，请检查后重试”。配置本机地址后，普通错误区域仍显示相同结论，但详情明确写“拒绝该 base_url：拒绝抓取非公网地址：127.0.0.1…”。一次完整错误区域中“API Key”为 `[83,1803][192,1840]`，“密钥无效…”为 `[83,2000][431,2045]`。这不是已得到供应商认证拒绝的证据。

用户影响：未配置的用户可能反复寻找、购买或更换密钥；地址被拒绝的用户可能反复编辑正确密钥。系统给出的修复方向与详情里的原因不一致。

建议：根据实际错误区分“尚未配置”“地址被拒绝”“网络连接失败”和“认证失败”；只有认证错误才显示密钥无效。当前无密钥时不要展示容易暗示“已有密钥但错误”的固定圆点字段。默认恢复按钮直接指向相应设置项，并使用用户能理解的说明。

### 2. P2：从历史重开当前会话会无提示丢失未发送草稿

**状态：已验证并重复。**

复现：① 在 `盲测-20261003-人机工效` 输入“盲测未发送草稿：G1南京南到上海虹桥票价”，不发送；② 点历史；③ 点回同一会话条目。

证据：操作前输入节点为 `EditText '盲测未发送草稿：G1南京南到上海虹桥票价' [81,2138][843,2264]`，查询按钮已启用。点历史中该会话（条目 `[42,838][761,1013]`）后，输入节点变为空，出现“继续追问…”，查询按钮禁用。没有确认或撤销提示。此前点击“换个日期”生成的草稿在重开会话后也变为空；新建空对话再回旧会话，同样没有恢复草稿。

用户影响：仅为了查历史或重新定位当前会话，就损失已输入的车次、日期和站点内容。长追问的重输成本会更高，用户难以预测哪些导航会清空输入。

建议：按会话保存草稿；选择当前会话时保留输入；建立新对话时也保留旧会话草稿。若必须清空，给出可撤销的提示。优先实现保留，避免额外确认打断正常导航。

### 3. P2：降级回复和技术性错误占据主要阅读空间，核心结果的状态不够清楚

**状态：已验证文字与布局；视觉 Markdown 渲染未覆盖。**

复现：① 在未配置模型或上述失败设置下发送票价问题；② 阅读回复和错误区域；③ 展开错误详情，再查询单独的 G1 时刻表。

证据：票价答复的一个可读文本节点同时包含“未经模型归纳、组织与校对”、`time=明天`、`direction=北京南→上海虹桥`、`ticket.price: ok`、完整接口 URL 和再次说明非大模型输出；层级文本还保留 `**`、`###`。实际结果后又有模型错误区域及密钥错误。单独时刻查询虽已返回完整七站卡片，滚到最底时主要可见区域仍是模型错误与密钥提示。详情包含 `.env`、`LLM_ALLOW_PRIVATE_BASE_URL=true`、`LLM_PROVIDERS_FILE` 等面向开发环境的操作说明。

用户影响：用户首先需要从技术状态中辨认“票价/时刻检索已成功”，还要理解“模型不可用”究竟会影响数据正确性还是表述方式。读完结果后落到错误区域，容易把可用数据整体当作失败。可访问文本含原始标记也会增加辅助技术阅读负担；是否视觉同样显示原始标记，需另行截图验证。

建议：使用简短状态：“已查到票价/图定时刻；智能解读暂不可用”，把成功的数据放在主要层级。技术调用、URL 及开发环境设置放进可展开详情；默认错误只说明影响范围和可执行恢复方式。可访问文本使用整理后的自然语言，不暴露 Markdown 控制标记。

### 4. P2：降级处理复合问题时只返回其中一项，未明确说明遗漏的需求

**状态：已验证于模型不可用路径；不能推广到模型正常时。**

复现：在同一测试会话发送“盲测：明天G1从北京南到上海虹桥各站时刻、停站和票价是什么？”。

证据：答复列出的已调用项只有 `ticket.price: ok`，内容只给票价、起终时间和历时，没有各站时刻及停站。之后单独发送“盲测：明天G1时刻表”，能返回北京南、沧州西、德州东、曲阜东、南京南、苏州北、上海虹桥的结构化表，说明本次环境中各站检索可得到数据。复合答复只泛称模型当前不可用，没有直说“各站时刻和停站尚未查询”。

用户影响：用户可能误以为需求已被完整处理，或把缺项理解成没有数据；需要自己拆题和重新输入。对于首次使用者，单次自然语言提问的预期与返回内容范围不一致。

建议：降级模式识别多个需求时分项处理，或显式列出“已完成：票价；尚未完成：各站时刻、停站”，提供可编辑的补查入口。优先诚实说明结果范围，不要求用户从技术调用名反推遗漏项。

### 5. P3：纯粹回看旧内容也提示“有新内容”

**状态：已验证。**

复现：① 等待 G1 时刻回复完成并到达底部；② 不再发送或生成内容；③ 上滑到此前的站点；④ 点回到底部。

证据：查询按钮处于普通的禁用状态，已经没有“停止生成”；只执行阅读滑动后，底部显示“有新内容 · 回到底部”，可点击区域 `[292,1852][789,1978]`。点击后该入口消失。此前文本回复也可观察到同样文案。

用户影响：“有新内容”会使用户以为后台刚更新了时刻或新生成了答案，干扰对数据时效的理解。按钮行为本身能完成返回底部。

建议：离开底部但没有新增内容时只显示“回到底部”；只有离开底部期间实际新增消息时，才显示“有新内容”或新增条数。

### 6. P3：“换个日期”给出没有日期的草稿，还需要用户自行推断下一步

**状态：已验证。**

复现：在 G1 时刻卡片状态点“换个日期”。

证据：输入框填入“查一下 G1 其他日期的时刻表”，并打开键盘；没有给出具体日期、明确占位符或日期选择入口。本次没有发送这条含糊草稿，因此未推断服务器会如何解释。

用户影响：用户知道想换日期，但还需辨认该改哪段、应输入什么格式；直接发送的结果可能不符合目标日期，这一后续风险仅为推断。

建议：打开日期选择层，或填入“查询 G1 在【日期】的时刻表”并选中日期占位符；保留用户编辑和确认发送的控制。

## 已验证、推断与未覆盖的区分

已验证结论集中于：示例填草稿、提供商选择层、缺字段/失败反馈、保存返回会话、降级票价和时刻结果、七站长卡片滚动、详情展开、回到底部、历史搜索与改名、删除取消、草稿丢失，以及进程重启后密钥字段为空。这些均依据客户端实际操作。

推断集中于：错误文案可能诱导更换密钥、含糊日期草稿可能造成错误日期、长草稿丢失成本更高。没有实际购买、真实密钥认证或错误日期请求来证明这些后果。

未覆盖：真实供应商的成功连接和恢复、付费模型回答质量、持续流式生成和停止结果、全部提供商、独立阅读模式、所有历史条目数量下的性能、深色主题、放大字体、横屏、其他设备、TalkBack 连续朗读、文字对比度和纯视觉美观。没有将“本次没发现入口”写成功能不存在。

## 总体判断与优先顺序

原生客户端的基本入口、示例、历史搜索、触控面积和结构化时刻表具备可用基础；本次没有遇到无法继续操作的阻断。模型不可用时仍能获取列车数据是一项实际价值，但失败状态解释不准确、技术信息过重，降低了用户对结果的理解和信任。历史导航清空草稿则是可以直接复现的内容保护问题。

最值得优先修复的三项：

1. 准确区分未配置、地址拒绝、网络失败和认证失败，去掉错误的“密钥无效”归因。
2. 按会话保留未发送草稿，重开当前会话不清空输入。
3. 整理降级状态：突出已成功的数据，明确未完成的需求，折叠技术细节。问题 3 和 4 应一起考虑，避免只缩短错误文案却继续隐去缺项。

本报告仅提出评价和建议，没有实施修复。
