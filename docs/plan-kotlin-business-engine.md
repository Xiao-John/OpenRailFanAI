# Kotlin 共享业务引擎远期计划

- 记录日期：2026-09-29
- 状态：候选计划，未启动实施。
- 授权范围：本次仅记录评估与计划，不授权重构 Python 或迁移数据源。
- 与当前工作的关系：Android Compose 与 KMP 客户端解耦继续按原计划进行；本计划不改变其范围，不阻塞当前交付。

## 目的与结论

未来可考虑将设备内 Python 业务逻辑迁入 Kotlin Multiplatform（KMP），由 Android Compose 和 iOS SwiftUI 分别呈现界面，共享查询编排、领域规则与数据源适配逻辑。

技术上可行，但总体工作量较大。主要成本是现有工具依赖的替代、跨平台网络验证和历史业务行为的等价性验证，不是语法翻译。当前不承诺排期、代码共享比例、包体降幅或查询速度提升。

完整解除移动端 Python 依赖后，才可能移除 CPython、Chaquopy、本地 FastAPI 和 Uvicorn，减少包体与启动环节。只要仍有必需功能依赖 Python，就不能将上述收益计为已经实现。

## 现有依赖与重构依据

现有工具与接口细节见 [数据源说明](datasources.md)，后端架构见 [实现总览](EXPL.md)，设备内运行方式见 [Android 文档](android.md)。以实际代码和锁定版本为最终依据，文档中的接口描述不保证始终有效。

当前 `backend/app/tools/_rt12306.py` 直接导入 `mcp_12306.services.ticket_service` 的查询函数；`backend/requirements-nodeps.txt` 说明项目复用其业务代码，未运行完整 MCP 服务链路。因此，此处“重构 MCP 工具”主要指替代工具内部实现，不能仅通过更换 Kotlin MCP 客户端完成。

未来重构可能需要依据相应开源项目的文档、源码、测试和接口说明，重新实现所需工具。启动前应逐项记录上游仓库、版本或提交、许可证、使用的具体模块及已知行为。文档不足时不能猜测接口契约，须结合源码和实际响应确认。

开源工具文档不等于数据提供方承诺稳定的公开 API。重构后仍需遵守既有访问约束、限流与缓存规则，并验证数据源实际可达性。若复用或移植上游代码、数据或资源，应保留适用的许可与署名要求。

## 范围与难度评估

| 部分 | 迁移判断 | 主要风险 |
|---|---|---|
| 数据模型、展示协议、字段校验 | 较适合迁移 | 缺失值、默认值、版本与降级语义 |
| 日期、车次解析、上下文处理 | 较适合迁移 | Unicode 正则、时区、历史边界样例 |
| 工具编排、并发、取消与降级 | 可行，验证量较大 | 异常传播、竞态、部分成功与重复终态 |
| 云端模型接入 | 可行 | 供应商差异、API 方言、流式事件、用量统计 |
| 12306 工具 | 难度较高 | Python 库隐含行为、站点解析、网络引擎与实际接口变化 |
| rail.re、径路及其他 HTTP 工具 | 逐项评估 | 响应解析、日期归属、缓存及可达性 |
| 拼音纠错、字典与网页解析 | 替换成本待调查 | 多平台库、数据来源、解析一致性 |
| FastAPI 与 Uvicorn | 移动端可不再需要 | 浏览器版仍需单独保留或提供服务端入口 |

HTTP、JSON 与协程等基础能力有多平台实现可用，但这不能证明现有数据源可无差别替换。可参考 [Kotlin 序列化](https://kotlinlang.org/docs/serialization.html) 和 [Ktor SSE 客户端](https://ktor.io/docs/client-server-sent-events.html)，具体版本与目标平台能力在正式立项时重新核查。

## 候选架构

共享业务引擎负责数据模型、领域规则、查询编排和结果事件；平台层负责网络引擎、密钥、文件、系统生命周期及其他原生能力。共享部分应进入 KMP `commonMain`，不依赖 Android 或 JVM 专用 API。

原生客户端可直接调用业务引擎并订阅结果事件，无需为了复刻旧架构而继续启动手机内 HTTP 服务器。若未来仍需浏览器服务，可在业务引擎外增加服务端适配，或暂时保留 Python 服务；两种路线均尚未决定。

本计划与当前共享客户端逻辑有区别：当前 KMP 客户端消费 Python 后端协议；本计划若正式实施，才逐步把后端职责移入共享引擎。过渡中应复用已经建立的模型与契约，避免重复建设。

## 候选阶段与决策门槛

以下仅是未来立项时的分阶段设想，不是交给 L 的执行指令。

1. **依赖与行为盘点**：明确所有工具、上游实现、许可证、缓存、失败语义和既有测试，形成完整替代范围。
2. **关键可行性验证**：选取有代表性的 12306 查询及模型流式调用，确认 Android 和可用 Apple 环境中的网络行为。静态样例不能替代此项验证。
3. **纯逻辑迁移评估**：使用现有 Python 输出与固定样例对照领域规则、协议及状态转换，识别不等价行为。
4. **逐工具替代**：按明确边界替换并保留回退，避免长期维护两套无明确归属的完整规则。
5. **移除运行时评估**：必需功能全部脱离 Python 且完整回归通过后，再评估设备端移除运行时；不自动删除浏览器服务或 LM 依赖。

正式启动前需要单独明确用户授权、优先级和范围。Compose 主链路是否稳定、是否要求 iOS 无自建服务器运行、关键工具是否存在可接受的替代路径，将共同决定是否值得启动。

## 验证与收益判定

- 以行为等价为核心：图定时刻与实际运行状态、交路记录日期、空结果、截断、部分成功和失败降级的语义必须保留。
- Python 可作为过渡期对照实现；固定响应与错误注入适合日常比对，外部接口联调采用受控频率。
- Android 查询成功不能证明 iOS 网络引擎也能成功；目标平台独立记录验证状态。
- 同一 ABI、资源、字典和构建类型下比较包体、安装占用、冷启动与内存；查询耗时区分本地处理、模型生成及数据源网络。
- 不在依赖替代调查完成前给出工期或“完全跨平台”承诺。当前总体判断为高工作量，精确估算待立项评估。
